# Assumed shortcuts

One line per shortcut currently in the code, with the reason. Remove a line when the real implementation lands.

- **Templated questions for document chunks** ([src/dataset/question_gen.py](src/dataset/question_gen.py)): questions are built from the section heading and the document title with 2-3 fixed templates per language ("What does \"<document>\" say about \"<heading>\"?"). They are less varied than LLM-generated questions. This is an accepted trade-off: the content cannot be sent to an external LLM (same rule as the anonymiser), and every answer is copied from the chunk, so it can never be hallucinated. A local model, once approved, would plug in as another `QuestionGenerator`.
- **Templated rewriting of CRM facts** ([src/dataset/builders/facts.py](src/dataset/builders/facts.py)): factual answers (status of a claim, a policy, an invoice) come from templates keyed by (case_type, status, language). The "next step" sentence is chosen from the CATEGORY of the latest internal note (expert appointed, report received...), detected by keywords. The note is classified, never copied, but this is a fixed rewriting, not a free one. Reason: an internal note is not a customer-facing answer, and no LLM may see client content. A local model, once approved, would plug in next to the `QuestionGenerator` extension point, and its output would still pass the field-grounding check. Rejected claims deliberately have no template (`no_template_for_state`): they need a reasoned human answer.
- **FakeConnector** ([src/connectors/fake.py](src/connectors/fake.py)): 60 hand-written in-memory documents (incl. 3 exact duplicates, 2 near duplicates in the same thread, 1 empty, 1 ten-character, 1 off-topic). Reason: run the pipe end to end without any external source. dedup_near now keeps one record of each near-duplicate pair.
- **Small split settings in config.yaml** (`eval_floor_per_domain: 2`, `eval_floor_per_cell: 1`, `min_train_per_domain: 4`, all in examples): production values are 25 / 5 / 20 (config.production.yaml). Reason: with ~50 kept examples the production values would mark every domain INSUFFICIENT_DATA. Even so, floors get scaled down (factor shown in the report) to respect `eval_ratio_max`.
- **Synthetic CRM data in Postgres** ([src/synthetic/crm.py](src/synthetic/crm.py), loaded by `scripts/seed_crm.py`): invented customers, policies, claims, notes and invoices, texts composed from per-language sentence pools. Notes carry an `author_role`: `customer`, `agent` (a reply written TO the customer, tied to the request it answers, see [src/synthetic/crm_replies.py](src/synthetic/crm_replies.py)) or `internal` (staff only, never an answer); invoices carry an `agent_reply`. Reason: no real client data yet. The real schema will differ; only the `tables:` mapping in config.production.yaml should need to change.
- **Synthetic document folder** ([src/synthetic/documents.py](src/synthetic/documents.py), written by `scripts/generate_documents.py`): 14 invented PDF / DOCX files with deliberate traps (scan without text layer, mojibake, table, near-empty template, contradictory procedure versions). Reason: no client documents yet. The policy conditions are long enough to be chunked (9 sections) but fit on one page each.
- **Synthetic ticket export** ([src/synthetic/tickets.py](src/synthetic/tickets.py), written by `scripts/generate_tickets.py`): 121 threads / ~400 messages in a CSV, 15 of them re-exported as .eml. Texts come from per-topic sentence pools, with one unique opening per thread. Reason: no client mailbox yet. In the two exports of a thread, agent replies carry different reference numbers (ticket id vs mailbox id). That makes the pair near-identical rather than identical after cleaning, which is what a real dual export looks like.
- **Cross-language supersede is NOT detected** ([src/connectors/files.py](src/connectors/files.py)): `procedure_water_damage_v2.docx` (FR, 5-day deadline) and `procedure_waterschade_v3.docx` (NL, 8-day deadline) describe the same procedure, but their filenames and titles differ by language. Both currently reach the training set with contradictory deadlines. They are listed under "Needs client review" in the quality report. Reason: matching them reliably needs translation-level similarity, and a looser rule would silently merge unrelated documents. Fix options: a `supersedes:` mapping maintained by the document owners, or a shared document id in the file metadata.
- **Cross-source SEMANTIC duplicates are NOT detected**: 3 ticket threads discuss claims that also exist in the CRM `claim_notes` (same customer, same claim number, different wording). Near-duplicate detection is lexical (character shingles), so it does not link them, and they are not listed for review. Today only the ticket side becomes an example (CRM notes are rejected at build), but nothing would stop both sides once CRM timelines yield examples. Reason: catching them needs entity linking (claim number, customer) or embeddings. See README, "Known limitations".
- **Volumes tuned through the synthetic generators** (never through thresholds): 85 claims, 100 policy summaries, 60 invoice notes, 121 ticket threads give 599 examples (422 train / 177 eval), and every domain is MEASURABLE. The margins are thin: onboarding has exactly 25 eval examples and the total is 1 below the 600 target. Changing any generator parameter reshuffles the seeded draws, so a domain can tip back to PARTIALLY_MEASURABLE. Reason: synthetic data. With real data the volumes are whatever the client has.
- **Acceptance rates are high on synthetic data** (facts 99.5%, documents 94%, tickets 86.5%; 95% overall vs 19% before): the denominator changed, the rules did not. The CRM used to be 615 row-level candidates, all rejected; it is now 243 case bundles, and the facts builder only proposes what it can ground. Synthetic fields are always complete and well-typed, so `fields_insufficient` and `answer_not_grounded` never fire here (they do in the tests). On real CRM data, expect them to.
- **No OCR**: a PDF without a text layer is dropped with `pdf_no_text_layer` (see README, next steps).
